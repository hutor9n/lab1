Опис
У роботі потрібно розширити наявний backend односторінковим інтерфейсом, підключити
реляційну базу даних, реалізувати окремий застосунок міграцій і розгорнути рішення в
Kubernetes. Helm Chart має описувати всі компоненти, а CI — перевіряти та пакувати chart і
зберігати його в артефактах запуску GitHub Actions.

Мета лабораторної роботи

1.  Отримати повноціне розподілене рішення, що містить клієнта, баз даних та серверну

частину

2.  Навчитись розробляти Helm Chart для розподіленої системи
3.  Розширити CI додатковим кроком, що займається упаковкой Helm Chart.

Завдання №1. Розробити простого клієнта та розширити СI

В існуючий репозіторій додайте простий односторінковий клієнт (frontend application), що
отримує інформацію з серверу і надає можливість показувати список стуностей з якими
працює ваш сервер та редагувати їх. Наприклад, у разі якщо ваш сервіс відповідає за ротобу
з користувачами, він повинен надавати змогу додавати, видаляти, редагувати користувачів, а
також показувати список наявних користувачів в системі.

Умови:

1.  Ви можете розробити клієнта на будь-якому технологічному стеку (раджу Angular чи

React, але можете обрати будь що)

2.  Не забудьте створити для клієнта Dockerfile і додати його сборку в CI, артефакт

повинен розміщуватись в віповідному Docker registry так само як і для серверної
частини.

3.  Уважно налаштуйте конфігурацію, яка містить посилання на сервер, не забудьте що,

коли ви будете запускати клієнта в Pod він повинен дивитись на url, що задекларован в
вашому Ingress для поточного середовища.

Завдання №2. Додати до серверу базу даних та розробити job
(консольний додаток), що застосує міграцію.

Додати до існуючого серверу роботу з базою даних, використовувати Code-First підхід та
ORM, що відповідає технічному стеку вашого сервера.

Умови:

1.  Розробити консольний додаток, запуск якого застосовує міграції до вказаної бази

даних.

2.  Розробити для вишче вказного додатку Dockerfile й додати його сборку в СI, артефакт

повинен розміщуватись в віповідному Docker registry для подальшого доступу з
системи Kubernetes.

3.  Сервер повинен сберігати данні в базі даних.
4.  Уважно налаштуйте конфігурацію, що містить ConnectionString до бази даних,

раховуйте, що значення буде відрізнятися для різних середовищ.

Завдання №3. Розробити Helm Сhart для розгортання в системі
Kubernetes.

В конексті данної задачі, ви створите Helm Chart та розширете СI відповідним кроком, що
буде упаковувати поточні данні в Helm Chart та сберігати в артефактах GitHub.

В корені проєкту, створіть директорію k8s - це місце розташування вашого Helm Chart, саме в
цій директорії ви будете запускати команду helm create … і створювати ваш Helm Chart.

Умови:

1.  Helm Chart отримує інформацію про версію чарта та додатку з файлу Chart.yaml,

робити автоматичний розрахунок версій в поточній роботі не обовязково.

2.  Helm Chart встановлює всі компоненти розподіленого рішення.
3.  Файл README.md в кореневій директорії вашого репозіторію містить опис того як

упакувати чарт, як встановити і опис проєкта.

4.  values.yaml – містить параметри для ваших шаблонів, елементи Helm Chart такі як

Deployment, Service тощо повинні в бльшості використовувати параметри встановлені
в цьому файлі.

Додаток A. Ingress

Для лабораторної можна використати Ingress, який спрямовує /api до backend, а / — до
frontend.

Приклад декларації:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: lab-webapp
  namespace: webapp-lab
spec:
  ingressClassName: nginx
  rules:
    - host: webapp.lab.test
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: lab-api
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: lab-frontend
                port:
                  number: 80
Пояснення:

•

ingressClassName: nginx — ім’я наявного IngressClass, який обслуговує встановлений
NGINX Ingress Controller. Сам ресурс Ingress не встановлює контролер.

•  host — доменне ім’я застосунку, яке потрібно спрямувати через DNS або файл hosts на

доступну адресу контролера.

•  pathType: Prefix — зіставлення за префіксом шляху. Для /api/items застосовується

більш конкретне правило /api.

•  backend.service.port.number — порт Service, а не безпосередньо контейнера. Ingress і

обидва Service мають бути в одному namespace.

У цьому прикладі шлях не переписується: backend отримує /api/items. Тому анотація rewrite-
target не потрібна. Запити до API йдуть безпосередньо через Ingress; проксі /api/ у frontend
Nginx залишається корисним для доступу через port-forward.

Додаток Б. Корисні команди для роботи з Helm Chart
У прикладах:

•  charts/webapp — каталог Helm Chart;

•

lab — ім’я release, тобто встановленого екземпляра chart;

•  webapp-lab — namespace;

•

values.lab.yaml — файл налаштувань середовища.

Створення та перегляд chart
# Перевірити версію Helm
helm version

# Створити початкову структуру chart
helm create charts/webapp

# Переглянути метадані Chart.yaml
helm show chart charts/webapp

# Переглянути стандартні values.yaml
helm show values charts/webapp

# Переглянути довідку щодо команди
helm install --help

Перевірка та генерація Kubernetes-маніфестів
# Перевірити структуру й типові помилки chart
helm lint charts/webapp

# Перевірити chart із налаштуваннями середовища
helm lint charts/webapp -f values.lab.yaml --strict

# Згенерувати YAML без встановлення у кластер
helm template lab charts/webapp \
  -n webapp-lab \
  -f values.lab.yaml

# Зберегти згенеровані маніфести у файл
helm template lab charts/webapp \
  -n webapp-lab \

helm upgrade lab charts/webapp \
  -n webapp-lab \
  -f values.lab.yaml

# Встановити release або оновити, якщо він уже існує
helm upgrade --install lab charts/webapp \
  -n webapp-lab \
  --create-namespace \
  -f values.lab.yaml \
  --wait \
  --wait-for-jobs \
  --timeout 5m

helm get manifest показує маніфести, збережені Helm. Для перевірки поточного стану Pod,

Пакування chart
# Створити архів chart у каталозі dist
helm package charts/webapp --destination dist

# Задати версію chart та інформаційну версію застосунку
helm package charts/webapp \
  --destination dist \
  --version 0.1.5 \
  --app-version abc1234
# Переглянути метадані запакованого chart
helm show chart dist/webapp-0.1.5.tgz

# Встановити chart безпосередньо з архіву
helm install lab dist/webapp-0.1.5.tgz \
  -n webapp-lab \
  --create-namespace \
  -f values.lab.yaml

--version задає версію пакета chart. --app-version змінює поле appVersion, але не змінює
автоматично теги контейнерів.

Відкат і видалення
# Переглянути доступні ревізії
helm history lab -n webapp-lab

# Повернути release до ревізії 2
helm rollback lab 2 \
  -n webapp-lab \
  --wait \
  --timeout 5m

# Видалити release та керовані ним ресурси
helm uninstall lab -n webapp-lab
