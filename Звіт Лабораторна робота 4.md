## Хід роботи

### Завдання №1. Розробка клієнтського застосунку (Frontend) та розширення CI

#### 1.1. Розробка Single Page Application (SPA)
У підкаталозі `frontend/` було реалізовано адаптивний односторінковий клієнтський інтерфейс (`index.html`), який взаємодіє з сервером через REST API та підтримує повний набір операцій CRUD:
- Відображення таблиці наявних елементів (`ID`, `Назва`, `Опис`, `Ціна`) із можливістю оновлення в один клік;
- Форма додавання нового елемента з валідацією полів на клієнті;
- Редагування вибраного елемента (заповнення форми даними сутності, зміна заголовка на «Редагування елемента #ID» та збереження через HTTP `PUT`);
- Видалення запису за ідентифікатором через HTTP `DELETE` із діалогом підтвердження.

Клієнт динамічно налаштований на роботу через уніфікований префікс Ingress `/api/items`:
```javascript
const API_BASE = window.location.port === "8000" 
    ? "http://localhost:8000/api/items" 
    : "/api/items";
```

#### 1.2. Контейнеризація Frontend та конфігурація Nginx
Створено конфігурацію веб-сервера `frontend/nginx.conf`, що роздає статичні файли інтерфейсу та забезпечує внутрішній проксі `/api/` на сервіс `lab-api:8000`:
```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://lab-api:8000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Створено багатошаровий Dockerfile для фронтенду (`frontend/Dockerfile`):
```dockerfile
FROM nginx:alpine

COPY frontend/nginx.conf /etc/nginx/conf.d/default.conf
COPY frontend/index.html /usr/share/nginx/html/index.html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

### Завдання №2. Додавання бази даних та консольного додатку міграцій (Migration Job)

#### 2.1. Підключення реляційної СУБД та ORM (Code-First підхід)
До існуючого FastAPI серверу додано бібліотеку **SQLAlchemy 2.0**:
- У файлі `app/database.py` оголошено фабрику підключень `engine` та механізм отримання сесії `get_db`. Рядок підключення (`DATABASE_URL`) конфігурується через змінну середовища:
  - за замовчуванням для локального тестування використовується SQLite;
  - у контейнеризованому та Kubernetes середовищі передається ConnectionString до PostgreSQL.
- У файлі `app/models.py` створено декларативну модель `ItemModel`:
  ```python
  class ItemModel(Base):
      __tablename__ = "items"
      id = Column(Integer, primary_key=True, index=True, autoincrement=True)
      name = Column(String(128), nullable=False)
      description = Column(String(512), nullable=True)
      price = Column(Float, nullable=False)
  ```
- Усі ендпоінти в `app/main.py` адаптовано для роботи з базою даних через dependency injection `db: Session = Depends(get_db)`.

#### 2.2. Розробка консольного застосунку для міграцій (`app/migrate.py`)
Створено окремий застосунок `app/migrate.py`, що реалізує:
1. Механізм очікування готовності СУБД (Retry Loop до 30 спроб із паузою 2 с);
2. Створення та валідацію таблиць у базі даних за допомогою `Base.metadata.create_all(bind=engine)`;
3. Інформаційне логування створених таблиць та коректне завершення з відповідним кодом виходу (0 — успіх, 1 — помилка).

#### 2.3. Контейнеризація Migration Job (`Dockerfile.migration`)
```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

ENTRYPOINT ["python", "-m", "app.migrate"]
```

### Завдання №3. Розробка Helm Chart для розгортання в Kubernetes

У каталозі `k8s/webapp` розроблено повнофункціональний Helm Chart.

#### 3.1. Структура Helm Chart
```
k8s/webapp/
├── Chart.yaml                  # Метадані чарту (версія 0.1.0, appVersion 1.0.0)
├── values.yaml                 # Конфігураційні параметри за замовчуванням
└── templates/
    ├── _helpers.tpl            # Шаблони назв та міток (Labels)
    ├── db-secret.yaml          # Секрети доступу та DATABASE_URL
    ├── db-statefulset.yaml     # StatefulSet та PVC для PostgreSQL + Service
    ├── migration-job.yaml      # Kubernetes Job (Helm Hook post-install/upgrade)
    ├── api-deployment.yaml     # Deployment і Service для Backend API
    ├── frontend-deployment.yaml# Deployment і Service для Frontend
    └── ingress.yaml            # Ingress маршрутизація (/api -> API, / -> Frontend)
```

#### 3.2. Основні параметри `values.yaml`
- `database`: параметри образу PostgreSQL, реквізити користувача, розмір сховища (`1Gi`), налаштування `persistence`;
- `migration`: образ `hut0r9n/lab1-migration:latest` та `backoffLimit: 4`;
- `api`: кількість реплік, ресурси (`cpu`, `memory`), ім'я та порт сервісу `lab-api:8000`;
- `frontend`: кількість реплік, ім'я та порт сервісу `lab-frontend:80`;
- `ingress`: прапорець активації (`enabled: true`), клас контролера (`nginx`) та віртуальний хост `webapp.lab.test`.

#### 3.3. Верифікація Helm Chart (Linting & Rendering)
Виконано перевірку синтаксису чарту:
```bash
helm lint k8s/webapp
```
*Результат:* `1 chart(s) linted, 0 chart(s) failed`.

Згенеровано повний набір Kubernetes маніфестів локально:
```bash
helm template lab k8s/webapp
```
Усі ресурси (Secret, StatefulSet, Services, Deployments, Job, Ingress) коректно отримують значення з `values.yaml` та відповідають вимогам Kubernetes API.

### Завдання №4. Оновлення та розширення CI Workflow (`ci.yml`)

Головний файл CI [`.github/workflows/ci.yml`](file:///a:/Univer/CI-CD/Labs/.github/workflows/ci.yml) розширено для паралельного збирання всіх компонентів:
1. **`build-n-test`**: встановлення залежностей Python, проходження pytest та збереження результатів у артефакти;
2. **`docker-backend`**: збирання образу `hut0r9n/lab1-api:latest`;
3. **`docker-frontend`**: збирання образу `hut0r9n/lab1-frontend:latest` із контексту `frontend/Dockerfile`;
4. **`docker-migration`**: збирання образу `hut0r9n/lab1-migration:latest` із контексту `Dockerfile.migration`;
5. **`helm-package`**: лінтинг Helm Chart (`helm lint k8s/webapp`), пакування в tgz-архів (`helm package k8s/webapp --destination dist`) та завантаження архіва в артефакти запуску GitHub Actions (`helm-chart-webapp`).

У перевикористовуваному workflow [`.github/workflows/docker-pack-n-push.yml`](file:///a:/Univer/CI-CD/Labs/.github/workflows/docker-pack-n-push.yml) додано підтримку вхідних параметрів `dockerfile` та `build_context` для універсальної збірки будь-якого компонента.
